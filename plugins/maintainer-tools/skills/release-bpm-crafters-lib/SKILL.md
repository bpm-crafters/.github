# Release to Maven Central

bpm-crafters projects publish to Maven Central by **pushing to `master`** — `.github/workflows/master.yml` runs `./mvnw clean deploy -Prelease` (Central Portal publisher, `autoPublish=true`, GPG signing). There is no tag/dispatch trigger. Signing/Central secrets live only in CI, so **you never deploy locally** — the master push does it.

Follow the steps in order. Do not skip the approval gate.

## 0. Preconditions
- Run from a clean working tree. `git fetch origin` first.
- Confirm the repository matches the release model this skill assumes; abort and tell the user if any is missing:
  - `.github/workflows/master.yml` exists, triggers on `push` to `master`, and runs `./mvnw … deploy … -Prelease`.
  - `.github/workflows/release-notes.yml` exists and triggers on `milestone: closed`.
  - The default branch is `develop`; `master` is the release trigger and allows direct pushes.
- Read the project coordinates from the root `pom.xml` (the project's own `<groupId>`/`<artifactId>`/`<version>`, not the `maven-parent` ones in `<parent>`):
  - `<rootArtifactId>` — e.g. `process-engine-adapter-cib-seven-root`
  - `<groupId>` — e.g. `dev.bpm-crafters.process-engine-adapters`
  - `<currentVersion>` — must be `<something>-SNAPSHOT`
- Confirm every change intended for this release is already merged into `develop`.

## 1. Ask for the versions (AskUserQuestion)
Use **AskUserQuestion** to confirm:
- `releaseVersion` — calendar scheme `YYYY.MM.n` (e.g. `2026.08.1`). Offer the SNAPSHOT-implied version and the next-month option; let the user pick or type one.
- `nextDevelopmentVersion` — the next `-SNAPSHOT` (e.g. `2026.08.2-SNAPSHOT`).

Do not infer these silently — the maintainer wants explicit control over the version.

## 2. Milestone + release notes source (notes are MANDATORY)
Release notes are generated by `release-notes.yml` on **milestone close** (draft GitHub release, notes from the milestone's issues/PRs).
- Create (or rename an empty leftover) milestone titled exactly `<releaseVersion>`.
- Assign every PR/issue merged since the last release tag to it:
  `git log --oneline <lastTag>..origin/develop | grep -oE '#[0-9]+'` → `gh pr edit <n> --milestone "<releaseVersion>"`.
- **Gotcha:** the notes generator groups by **label**. PRs without a label (typically the big `feat:` PRs) get **dropped** from the generated notes. Either label them first (`Type: enhancement`) or plan to hand-edit the draft in step 7.

## 3. Release branch + version bump
```
git checkout -B release/<releaseVersion> origin/develop
./mvnw versions:set -DnewVersion=<releaseVersion> -DgenerateBackupPoms=false -DprocessAllModules=true
```
- Do **not** pass `-DskipExamples` — the `examples` profile is active by default (`!skipExamples`), so `versions:set` bumps the examples modules too. Skipping it leaves them at the old version (drift).
- Verify all POMs (root + every module + BOM + examples) now show `<releaseVersion>`; the parent `maven-parent` version must stay untouched.

## 3b. Update the compatibility table in `README.md`
The README has a `## Compatibility` table whose first row must be the release being cut. Its columns differ per repo (adapter version, engine version, API version, sometimes Spring Boot) — keep the existing columns and formatting, only add a row at the top.
- Adapter version: `[<releaseVersion>](https://github.com/<owner>/<repo>/releases/tag/<releaseVersion>)` — link style as in the rows above.
- Engine version: the engine property in the root `pom.xml` (`cibseven.version`, `camunda.version`, `operaton.version`, …); if it is not a root property, take it from the module POM or `dependencyManagement` that pins the engine.
- API version: `process-engine-api.version`.
- Spring Boot (if the table has that column): `spring-boot.version`, in the granularity the existing rows use (usually `major.minor`).
- Also update any badge in the README header that carries the engine version (e.g. `Compatible with Operaton 2.1.3`).
Show the proposed row to the user and let them correct it before continuing; a wrong table is published with the release tag.

## 4. Local sanity build (no deploy)
```
./mvnw clean verify -B -ntp -T4
```
Must be BUILD SUCCESS across all modules before continuing.

## 5. Commit (signed)
```
git commit -am "Update versions for release"
```
The commit must contain the POM bumps and the README table row.
Confirm it is signed: `git cat-file commit HEAD | grep -i gpgsig` should show a signature header (local `%G?` may show `N` because there is no `allowedSignersFile` — that is fine; GitHub verifies against the registered key).

## 5b. Change overview before the gate
Before the approval gate, show the maintainer exactly what this release contains so they can
judge how safe it is. Reuse the data source from step 2 (`git log <lastTag>..origin/develop`),
no new mechanism.
- Collect the changes since the last release tag and deduplicate the PR references:
  `git log --oneline <lastTag>..origin/develop | grep -oE '#[0-9]+'`.
- For each PR fetch its metadata: `gh pr view <n> --json number,title,labels,author,mergedAt`.
- Print a Markdown table in the chat, sorted by merge date (newest first), with the columns
  **PR**, **Titel**, **Typ** (label), **Autor**:
```
| PR    | Titel                                  | Typ            | Autor    |
|-------|----------------------------------------|----------------|----------|
| #42   | feat: support Operaton 2.1             | enhancement    | emaarco  |
| #40   | fix: NPE beim Deployment               | bug            | someone  |
```
- Include direct-merge commits without an associated PR as their own rows (from the same
  `git log` line) so nothing is lost.
- Below the table, state the total count of PRs/commits in the release.

## 6. APPROVAL GATE → trigger the release (irreversible)
The maintainer has seen the change overview from step 5b. Prepare the master merge locally
first (safe, local only):
```
git checkout -B master origin/master
git merge --no-ff release/<releaseVersion> -m "Merge branch 'release/<releaseVersion>'"
```
Then **STOP** and ask for explicit approval with **AskUserQuestion**:
- header: `⚠️ Approval gate — irreversible step`
- question: `Push master and publish <releaseVersion> of <rootArtifactId> to Maven Central? Central versions cannot be deleted or overwritten.`
- options: `Publish now` — pushes `master` and starts the deploy; `Abort` — keeps everything local, nothing is published.

Only on `Publish now`:
```
git push origin master
```
On `Abort`: push nothing, leave the local `release/<releaseVersion>` and `master` branches as they are, and report their state so the user can resume or discard.

Watch the deploy:
```
gh run list --workflow=master.yml --branch master --limit 1
gh run watch <run-id> --exit-status
```
The "Deploy a new release version to Maven Central" step must succeed.

## 7. Release notes → publish
```
gh api --method PATCH repos/<owner>/<repo>/milestones/<number> -f state=closed   # triggers release-notes.yml
```
Wait for the "Milestone Closure" run, then review the **draft** release (`gh release view <releaseVersion>`).
- If a `feat:`/headline PR is missing (unlabeled — see step 2), edit the notes to add a Features section.
- Publish it pointing the tag at the **master release commit** (consistent with prior tags):
```
gh release edit <releaseVersion> --target <master-release-commit-sha> --notes-file <notes.md> --draft=false --latest
```
Confirm: `git ls-remote --tags origin <releaseVersion>` points at the release commit.

## 8. Bump develop to the next SNAPSHOT + carry the README row (via PR)
Always go through a PR — `develop` is protected by a ruleset in some repos (PR/squash, signed commits, required check "Build and run tests") and the flow should be identical everywhere.

This PR must also carry the step-3b compatibility row back to `develop`. The row was only added on the release branch (merged into `master`), so without this `develop`'s table still ends at the previous release — and the next release cut from `develop` silently drops the current row, leaving a gap in the published table.
```
git checkout -B chore/next-dev-version-<nextDevelopmentVersion> origin/develop
./mvnw versions:set -DnewVersion=<nextDevelopmentVersion> -DgenerateBackupPoms=false -DprocessAllModules=true
```
Re-apply the exact same `README.md` edit from step 3b on this branch: add the `<releaseVersion>` compatibility row at the top of the `## Compatibility` table (and the header engine badge if you updated it in 3b). The `versions:set` above leaves the POMs at `<nextDevelopmentVersion>-SNAPSHOT`, but the README row stays `<releaseVersion>` — same content as the row now on `master`.

**Gate — do not push until both are true.** This is the step that recurringly gets skipped, dropping the row from `develop`. After `git add -A`, before committing, confirm:
```
git diff --cached README.md   # MUST show the <releaseVersion> row added to ## Compatibility (and the badge if 3b changed it)
git diff --cached '**/pom.xml' # MUST show the <nextDevelopmentVersion>-SNAPSHOT bump
```
If the `README.md` diff is empty, STOP — the row was not re-applied; go back and add it. Do not push a branch whose staged diff lacks the compatibility row.
```
git commit -am "Update for next development version"
git push -u origin chore/next-dev-version-<nextDevelopmentVersion>
gh pr create --base develop --title "chore: set next development version <nextDevelopmentVersion>" --body "..."
```
The commit MUST contain both the POM bumps and the README compatibility row — a PR missing either is wrong and must not be merged. Wait for the "Build and run tests" check to pass, then `gh pr merge <n> --squash --delete-branch`.

> Note: a human-driven PR works because your commits are signed and attributed to your account, satisfying the ruleset. An Actions-bot PR would additionally need a GitHub App token (the stock `GITHUB_TOKEN` does not trigger CI) and an API-created commit for signing.

## 9. Verify
- Maven Central (direct repo, synced within minutes; the search index/UI may lag ~30 min). The root POM is published too, so check it with `<groupPath>` = `<groupId>` with dots replaced by slashes:
```
curl -s -o /dev/null -w "%{http_code}\n" \
  https://repo1.maven.org/maven2/<groupPath>/<rootArtifactId>/<releaseVersion>/<rootArtifactId>-<releaseVersion>.pom
```
  → expect `200`.
- GitHub release `<releaseVersion>` published as Latest, milestone closed, `develop` on `<nextDevelopmentVersion>`.
- The top compatibility row in `README.md` equals `<releaseVersion>` on **both** `master` and `develop` — assert both, so the row does not silently drop from the next release:
```
git show origin/master:README.md | grep -A3 '## Compatibility'
git show origin/develop:README.md | grep -A3 '## Compatibility'
```

## Report
Summarise: version released, artifacts on Central, release URL, develop version, and any manual notes fixes applied.
